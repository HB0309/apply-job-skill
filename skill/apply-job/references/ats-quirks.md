# ATS quirks & troubleshooting

Per-platform detail lives in `ats/<platform>.md`. This file holds the cross-platform failure modes.

- **Oracle CX auto-submit risk — see step 9.4.** A click that looks like ordinary form navigation can be the actual submit action there, with no separate confirm step. Verify page state after every click on Oracle CX and unfamiliar ATSes. Greenhouse was removed from this list 2026-09-08: its recorded "auto-submits" were the user submitting completed forms themselves during multi-link runs.
- **JS-rendered forms (Ashby, Greenhouse embeds, Workday) — VERIFY, don't trust the clicks (learned 2026-07-29, Crusoe).** On these forms, coordinate-based `computer` click+type and radio/toggle clicks can silently fail: the page auto-scrolls between screenshot and click, so typing lands nowhere and radio picks hit the wrong option. Symptoms: fields look filled in one screenshot but are empty/wrong on submit; a required Name/Email came out blank; a radio landed on the wrong choice (e.g. Race = White instead of Decline). **Before handing off, ALWAYS read the true field state with `javascript_tool`** (`document.querySelectorAll('input,textarea')` → name/value/checked). To FIX React-controlled inputs, set them via the native setter and fire events, not by typing:
  `const s=Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set; s.call(el,val); el.dispatchEvent(new Event('input',{bubbles:true})); el.dispatchEvent(new Event('change',{bubbles:true}));`
  For custom radios/toggles use `el.click()` on the backing `input`, or read the active toggle by computed `backgroundColor`. Prefer `read_page`→`form_input`(ref) where refs are exposed; fall back to JS when they are not. Never report a form "filled" from screenshots alone on these sites.
- Tectonic "Fontconfig error" lines are non-fatal noise — ignore unless the PDF fails to produce.
- If the master uses `fontspec` with a system font Tectonic can't find, tell the user which font and stop — don't swap fonts silently.
- If a form field type defeats `form_input`, try the computer tool (click + type). If a site blocks automation entirely, save the user a copy-paste pack (answers + resume path) and say so.
- **LinkedIn "SDUI Apply Flow" (`?openSDUIApplyFlow=true` on the Apply link) — read_page/find cannot see it at all. UPGRADED 2026-09-05: this is LinkedIn's CURRENT DEFAULT Easy Apply mechanism, not a rare variant.** First seen on BeaconFire Inc. (2026-09-05); confirmed again the same day on 2 more unrelated postings (First Quality, RK Infotech) — 3 for 3 LinkedIn Easy Apply links checked all carried `openSDUIApplyFlow=true`. **Treat every LinkedIn Easy Apply link as blocked until proven otherwise** — check for the URL param before investing prep time in a LinkedIn posting's fill phase, not after.
  LinkedIn's Easy Apply modal renders the entire form inside a Shadow DOM host (`#interop-outlet`), which the accessibility-tree walker does not traverse — `read_page` and `find` both report no modal/dialog exists even while it's visibly open on screen and passing a normal screenshot check. `file_upload` and `form_input` are unusable here since both require a `ref` from those tools. Confirmed via `javascript_tool`: `Array.from(document.querySelectorAll('*')).find(e=>e.shadowRoot)` finds the host, and the real file input/buttons are reachable by querying `host.shadowRoot.querySelectorAll(...)` directly — but that only gets you *reads*, not `file_upload`'s upload mechanism (which needs a real ref for the browser-side file-injection path, not a JS handle). **Do not attempt a blind fill here** — closing/discarding cleanly and reporting the block is correct; do not risk an unverified submit via JS-only interaction (`el.click()` on the wrong shadow-root button is easy to get wrong with no accessibility tree to sanity-check against).
  **Prep still runs normally (tailoring stays valuable — the user can submit the resulting PDF manually through the browser themselves); it's only the automated FILL step that should short-circuit.** During prep, once the real apply URL is known, check it for `openSDUIApplyFlow=true` and note the block in `form-pack.md` up front so the fill phase doesn't waste a `read_page`/`find` round-trip rediscovering it — go straight to "hand the user the browser, form is tailored and ready, they submit manually" instead. If this recurs: check whether `read_page`/`find` gain shadow-DOM support before retrying, or keep using the manual-handoff path the same way login walls already do.
- **SmartRecruiters "Easy Apply" (`oneclick-ui` apply pages, `jobs.smartrecruiters.com/.../oneclick-ui/...`) — worse than LinkedIn's single shadow root, treat as fully blocked (2026-09-05, Versant Media).** The entire form — every field, not just a modal — is built from Angular web components (`SPL-INPUT`, `SPL-FORM-FIELD`, `SPL-DROPZONE`, `SPL-AUTOCOMPLETE`, `SPL-PHONE-FIELD`, etc., SmartRecruiters' "SPL" component library), each carrying its own Shadow DOM. One real posting measured **37 separate shadow hosts** on a single apply page. `read_page`/`find` see almost nothing (just the top-level "Apply With Indeed" button) despite a fully-rendered, real form being visible on screen.
  **Do not attempt this via `javascript_tool` shadow-piercing either** — unlike LinkedIn's single host, this would mean correctly locating and driving 10+ independent Angular reactive-form inputs, each needing the right native-setter + event-dispatch sequence to satisfy Angular's change detection (get it wrong on even one and the value silently doesn't register, with zero accessibility tree to verify against). The blast radius of a partial/wrong fill here is much higher than LinkedIn's case. **Skip the automated fill entirely** — same manual-handoff pattern as LinkedIn SDUI: tailor and prep normally, note the block in `form-pack.md`, hand the user the browser with the tailored PDF ready. If this recurs on another SmartRecruiters `oneclick-ui` posting, don't re-attempt without checking first whether `read_page`/`find` have gained shadow-DOM support.
